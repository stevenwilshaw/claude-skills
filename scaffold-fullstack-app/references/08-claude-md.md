# <project>

npm-workspaces monorepo: `apps/api` (Express + Postgres), `apps/web` (Vite + React SPA), `packages/shared` (zod schemas + DTO types used by both, import as `@app/shared`).

## Commands
- `cp .env.template .env`, `npm install`, `npm run db:up`, `npm run migrate`, `npm run dev` (api :3000, web :5173; Vite proxies `/api`)
- `npm run typecheck` · `npm test` (unit, no Docker) · `npm run test:int` (integration; needs Docker running, Testcontainers starts Postgres[, MinIO])
- `npm run migrate:create -- <name>` creates a SQL migration; `npm run build`; `docker build -t <project> .`
- <if storybook> `npm run storybook`
- `apps/web/src/routeTree.gen.ts` is generated by the router plugin (`vite dev`/`vite build`); do not edit it by hand.

## Architecture rules (deliberate - do not "improve")
- **No ORM, no query builder, no DI framework, no UI framework.** Raw SQL via `pg`; manual wiring in `apps/api/src/container.ts`.
- **API feature = folder in `apps/api/src/features/<name>/`** with `<name>.routes.ts` (function returning a Router; zod validation lives here), `<name>.handlers.ts` (function; HTTP <-> controller only), `<name>.controller.ts` (class; repository/services injected via constructor; no `req`/`res`; business rules and `HttpError`s), `<name>.repository.ts` (class; `Db` injected; raw SQL, SQL aliases for camelCase, no mapper layer). Tests sit next to the files: `*.test.ts` (unit, fake deps) and `*.int.test.ts` (real DB). Use `features/posts` as the template for a new feature, then register it in `container.ts` and `app.ts`.
- **Validated input** is read with `valid<...>(res)` (set by the `validate` middleware in `res.locals.valid`; Express 5 `req.query` is read-only).
- **Schema changes** are plain SQL files in `apps/api/migrations` (`-- Up Migration` / `-- Down Migration`). Never edit an applied migration; add a new one. Migrations run automatically before the server starts in Docker.
- **Shared contracts** (zod schemas, DTO types) go in `packages/shared`; both apps import them.
- **Web routes are thin**: `src/routes/**` only declares routes (path, loader, component). UI lives in `src/features/<feature>/<list|view|create|edit>/`. Put a component next to the one screen that uses it; if two screens in a feature share it, move it to the feature root; if several features share it, move it to `src/components`.
- **Inputs vs fields**: `src/components/inputs/*` are form-agnostic (plain `value`/`onChange`). `src/components/form/*Field` wrap them with TanStack Form's `useFieldContext` and are registered in `useAppForm`. New input = base input + Field wrapper + registration.
- **No forms on list pages.** A list screen only lists. Add/edit forms go on a separate screen (`create/`, `edit/` route) or in a modal, never inline on the list. Delete confirmations and similar single-control actions (Popover) are fine on the list.
- Server state via TanStack Query (query options factories in `<feature>.queries.ts`); HTTP via the shared axios instance in `src/lib/api.ts`. Popovers use floating-ui, animation uses `motion`, icons `lucide-react`.
- Timestamps come back from the API as ISO strings (custom type parser in `db/pool.ts`).

## Auth (BetterAuth)
- Mounted at `/api/auth/*` in `app.ts` **before** `express.json()` (it reads the raw body). Tables are camelCase and quoted; they live in the first migration. Protected routes use `requireAuth`; the user is in `res.locals.user`. In tests, stub `requireAuth` (insert the user row first - FK on `posts.author_id`).
<if Keycloak>
## Auth (Keycloak BFF)
- The API is the OIDC client (PKCE + client secret); tokens stay server-side in a Postgres session store; the browser only has an httpOnly `sid` cookie. Never put tokens in the SPA. Dev Keycloak: http://localhost:8080 (admin/admin), dev user `dev`/`dev`; realm config in `docker/keycloak/realm.json`. Non-GET `/api` requests need `X-Requested-With: XMLHttpRequest` (CSRF guard). Do not add `offline_access` to the scope.
<if images>
## Images
- Originals + thumbnails are stored in MinIO/S3 under `posts/<id>/...` and always read through the API (no presigned URLs). Upload is a second request (`PUT /api/posts/:id/image`) after the post is saved. `ObjectStorage` wraps the S3 client; `PostImagesService` does validation and thumbnails (sharp).

## Gotchas
- Integration tests need Docker; they never use the compose database.
- `docker compose up --wait` fails on one-shot containers, so `db:up` is split in two steps.
- Keep `DATABASE_URL`/`APP_URL` ports in `.env` consistent with `POSTGRES_PORT`/`WEB_PORT`.
- Dockerfile runs from `/app/apps/api` on purpose (workspace layout keeps nested `node_modules` resolvable).
